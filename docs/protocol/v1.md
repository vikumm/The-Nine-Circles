# Protocol v1

Status: VS-020 hardening and observability gate.

## Package

The stable Protobuf package is `divinity.protocol.v1`.

C# generation uses namespace `Divinity.Contracts.V1` through `Grpc.Tools` and `Google.Protobuf`.

## Envelope Rules

Client messages are wrapped in `ClientEnvelope`:

- `protocol_version`;
- `sequence`;
- `client_tick`;
- exactly one client intent payload.

Server messages are wrapped in `ServerEnvelope`:

- `protocol_version`;
- `server_tick`;
- `ack_sequence`;
- exactly one server payload.

The conceptual envelope size limit is 64 KiB. Gateway code must reject larger payloads before expensive parsing.

## Server Authority

Client payloads are intents only. The v1 client contract does not allow clients to send:

- final damage;
- XP grants;
- currency grants;
- loot rarity;
- item instance ownership or attributes;
- completed cooldowns;
- stun durations;
- skill ranks;
- kill ids;
- equipment durability;
- final MP;
- collision resolution;
- final authoritative position;
- death decisions.

## VS-003 Gateway Smoke

`POST /protocol/v1/client-hello` accepts `application/x-protobuf` bytes containing a `ClientEnvelope` with `ClientHello`.

When called through the compatibility handler without a ticket store, this endpoint remains a protocol smoke check only:

- it validates size, Protobuf parsing, `protocol_version` and payload type;
- it returns a controlled `ServerEnvelope` response;
- it does not authenticate, consume tickets, open WSS, create sessions or route gameplay.

## VS-006 Game Ticket

Platform API issues a short-lived game ticket through `POST /launcher/game-ticket` after launcher authentication has produced an account identity.

The issue request binds the ticket to:

- account id resolved server-side;
- `buildId`;
- `protocolVersion`;
- `nonce`.

The response contains the bearer `gameTicket`, `expiresAtUtc` and `ttlSeconds`. The ticket TTL is 30 seconds.

Game Gateway consumes the ticket from `ClientHello.game_ticket` when it receives the VS-006 HTTP smoke request or the VS-007 WebSocket handshake.

Consumption rules:

- the ticket is single-use;
- consume is atomic in the configured shared store;
- malformed, missing, invalid, expired, reused, build mismatch, protocol mismatch and nonce mismatch are rejected with controlled `ServerError` responses;
- the VS-006 HTTP smoke route returns `CLIENT_HELLO_ACCEPTED_NO_SESSION` and does not create a durable WebSocket session.

Ticket secrets must not be placed in URLs, logs, traces or CLI arguments.

## VS-007 WSS Session Flow

Local development uses `ws://` and production deployments must terminate TLS before exposing this route as WSS.

`GET /protocol/v1/ws` accepts a WebSocket upgrade request. Anonymous handshake attempts are rate limited to 3/min per remote address before the socket is accepted.

Message order:

1. Client sends `ClientEnvelope.ClientHello`.
2. Gateway validates size, Protobuf shape, protocol version and `game_ticket`.
3. Gateway consumes the ticket once and creates an authenticated world session.
4. Gateway replies with `CLIENT_HELLO_ACCEPTED_SESSION`.
5. Client sends `ClientEnvelope.JoinWorld`.
6. Gateway verifies the requested character against the authenticated account and acquires a session lease.
7. Gateway replies with `JoinAccepted` when the lease is acquired.
8. Client sends `Heartbeat` to renew the lease.

`ReconnectRequest` is implemented by VS-018 after a fresh authenticated `ClientHello`; the reconnect token is short-lived, one-time and server-issued.

Since VS-008, the Gateway verifies `JoinWorld.character_id` against the persisted Knight owned by the authenticated account.

Normal WebSocket disconnect releases the VS-007 in-memory lease and records a session event. Abrupt-combat grace and full reconnect reassociation remain later work.

## VS-008 Knight Character Flow

Platform API exposes:

- `POST /characters/knight` to create the single VS-008 Knight slot for the authenticated account;
- `GET /characters/knight` to select the existing Knight for the authenticated account.

The creation request contains only `name`. The server normalizes and validates the name, reserves it globally, fixes vocation to `Knight`, assigns level 1 catalog stats and stores the safe spawn.

The client does not provide class, level, HP, MP, final position, map authority or ownership.

`JoinWorld` is accepted only when:

- the WebSocket session is authenticated;
- the requested `character_id` exists;
- the persisted character belongs to the authenticated account;
- no other active connection owns the character lease.

On accepted join, the Gateway ignores client-provided map/content authority and returns server-side values in `JoinAccepted`:

- `character_id`;
- `map_id`;
- `channel_id`;
- safe-spawn position;
- level, HP and MP;
- content hash.

The Gateway then sends a minimal `WorldSnapshot` containing the player entity at the server-defined safe spawn.

## VS-010 Authoritative MoveIntent

After `JoinWorld` is accepted, the client may send `MoveIntent` payloads through the authenticated WebSocket session.

Supported movement modes:

- `MOVEMENT_MODE_DIRECTION` for WASD-style normalized direction intent;
- `MOVEMENT_MODE_CLICK_TARGET` for a click target coordinate.

Authority rules:

- the client sends direction or target only;
- the client must not send final position, trusted speed, collision result or teleport authority;
- the Gateway rate limits `MoveIntent` to 20 messages per second per authenticated session;
- World Runtime owns normalization, facing, max displacement, bounds, collision, character state and sequence acceptance;
- repeated or older sequence numbers are rejected with a correction and no movement;
- dead or stunned characters are rejected with no movement;
- accepted movement may produce a `WorldSnapshot` at the 10 Hz server snapshot cadence.

Rejected movement returns either:

- `Correction` with the authoritative current position when the client must resync;
- `ServerError` with `ERROR_CODE_MOVE_REJECTED` for gateway/rate/protocol rejection.

Position checkpoints are written by server authority every 10 seconds, on normal disconnect and during graceful gateway shutdown.

## VS-011 Prediction and Reconciliation

VS-011 does not change Protobuf field numbers or add new messages. It uses:

- `ClientEnvelope.sequence`;
- `ClientEnvelope.client_tick`;
- `MoveIntent`;
- `ServerEnvelope.ack_sequence`;
- `WorldSnapshot`;
- `Correction`.

Client prediction rules:

- local prediction is visual and reversible;
- the client may render the own player immediately after sending direction or click-target intent;
- pending local intents with `sequence <= ack_sequence` are discarded;
- remaining pending intents are reapplied after each accepted authoritative snapshot;
- stale snapshots must not overwrite newer local or reconciled state;
- `Correction` and `WorldSnapshot` both override local prediction;
- small visual error is corrected smoothly;
- large visual error snaps to the reconciled authoritative state.

The client still must not send final position, collision authority, speed authority, checkpoint state or any gameplay outcome.

## VS-013 Basic Attack

After `JoinWorld`, the client may send `AttackIntent` with:

- `target_entity_id`;
- `skill_id`;
- `action_id`.

For VS-013, only `knight_basic_slash` is implemented. The intent remains client input only; it does not include damage, crit, target HP, death or cooldown completion.

World Runtime validates:

- attacker exists and is alive/not stunned;
- target exists, is alive and is in the same map/channel;
- attack sequence has not already been accepted;
- skill id is `knight_basic_slash`;
- server cooldown is complete;
- target is within 1.5 units;
- line to target is not blocked.

Accepted attacks return `CombatEvent` with `HIT` or `CRITICAL`, server-calculated damage and target HP after damage. Rejected attacks return `ServerError` with `ERROR_CODE_ATTACK_REJECTED`, except cooldown resync may return `SkillStateChanged`.

`SkillStateChanged` is a server payload for skill cooldown state. It is not a proof of client authority and must not be treated as client-owned cooldown completion.

## VS-014 Shield Bash

After `JoinWorld`, the client may send `CastIntent` with:

- `skill_id`;
- `target_entity_id`;
- `action_id`.

For VS-014, only `knight_shield_bash_r1` is implemented. The intent remains client input only; it does not include MP cost, final MP, damage, stun duration, skill XP, skill rank, target HP, death or cooldown completion.

World Runtime validates:

- caster exists, is a Knight and is alive/not stunned;
- target exists, is alive and is in the same map/channel;
- cast sequence has not already been accepted;
- `action_id` has not already produced a valid Shield Bash hit;
- skill id is `knight_shield_bash_r1`;
- MP is at least 10;
- server cooldown is complete;
- target is within 1.4 units;
- line to target is not blocked.

Accepted casts apply server-side damage, start a 5 second cooldown, spend 10 MP, apply a 1.25 second stun to the target and grant +1 Shield Bash skill XP. Rank is capped at 2 and rank 2 requires 20 XP.

Accepted casts may return:

- `CombatEvent` with server-calculated damage, target HP and `StatusEffectApplied(effect_id = "stun", duration_ms = 1250)`;
- `SkillStateChanged` with server cooldown timing;
- `CharacterProgressed` with server-authored skill XP and rank.

Rejected casts return `ServerError` with `ERROR_CODE_CAST_REJECTED`, except cooldown resync may return `SkillStateChanged`.

`CharacterProgressed` is a server payload. Clients may render it, but must not infer authority to assign XP, rank or progression locally.

## VS-015 Death And Respawn

VS-015 adds server-authored death, respawn, monster kill identity and preliminary durability exposure.

Character death rules:

- World Runtime decides when HP reaches zero;
- dead characters enter `Dead` server state and movement is rejected;
- death applies `StatusEffectApplied(effect_id = "death_screen", duration_ms = 5000)` through `CombatEvent`;
- respawn is due after 5 seconds and returns the character to the server Safe Spawn;
- XP, level and skill XP are not lost.

Monster death rules:

- the first valid lethal hit assigns a unique `CombatEvent.kill_id`;
- repeated or delayed attacks against the same dead monster return rejection and do not produce another kill id;
- loot and pending reward are intentionally still out of scope until later tasks.

Preliminary equipment durability:

- durable equipped items lose 1 durability on the character death transition;
- item durability never drops below zero;
- zero-durability equipment remains equipped but `EquipmentItem.attributes_active = false`;
- `InventoryDelta.equipment` may expose `durability`, `max_durability` and `attributes_active`;
- clients may display those fields, but must not calculate authoritative durability, equipment validity or stat contribution locally.

## VS-017 Inventory And Equipment

After `JoinWorld`, the client may send:

- `EquipItemIntent` with `item_instance_id`, `slot` and the last acknowledged `inventory_version`;
- `UnequipItemIntent` with `slot` and the last acknowledged `inventory_version`.

The intent remains client input only. It does not include owner, local item location, rarity, bind state, durability edits, defense, block chance, currency grants or pending reward authority.

Server authority rules:

- inventory state has exactly 20 slots;
- item moves, equip and unequip require the current optimistic `inventory_version`;
- the server validates item owner, current location, class restriction, minimum level, target slot, bind state and durability state;
- MMO-VS1 only supports `EQUIPMENT_SLOT_OFF_HAND`;
- Wooden Shield Normal grants +3 defense, Good grants +4 defense and +1% block, Rare grants +5 defense and +2% block;
- zero-durability equipment may remain equipped but returns `attributes_active = false` and grants no effective attributes;
- equip binds the item to the character;
- unequip returns the item to the first free inventory slot and fails without item loss when the inventory is full.

Accepted mutations return `InventoryDelta` with the updated `inventory_version`, occupied slots, equipment durability/activity and currency balance. Rejected mutations return `ServerError` with `ERROR_CODE_INVENTORY_REJECTED`.

Pending rewards are server-owned read model state. Claiming pending reward into inventory is implemented in server rules and requires a free slot; the public protocol claim command is intentionally deferred until a future task defines that client route.

## VS-018 Reconnect

`JoinAccepted` now includes a short-lived `reconnect_token` and `reconnect_ttl_seconds`. The token is server-generated, bearer-style, stored only as a hash by the gateway and rotated on successful reconnect.

Reconnect flow:

1. Client authenticates again with `ClientHello.game_ticket`.
2. Client sends `ReconnectRequest` with the last `reconnect_token` and `previous_connection_id`.
3. Gateway validates account ownership, token hash, token expiry, previous connection and active lease.
4. Gateway explicitly transfers the lease to the new connection and invalidates the previous connection for that actor.
5. Gateway returns `JoinAccepted`, authoritative `WorldSnapshot` and current `InventoryDelta`.

Authority rules:

- reconnect grace is 30 seconds total;
- abrupt disconnect during recent combat retains the world actor for up to 10 seconds;
- after grace expiry, the server saves a checkpoint and removes the actor from the map;
- unsafe checkpoints are converted to Safe Spawn;
- reconnect never replays old `RewardGranted` payloads;
- clients must not restore HP/MP, position, XP, inventory or equipment from local cache as authority.

Rejected reconnect returns `ERROR_CODE_RECONNECT_REJECTED`.

## VS-020 Hardening And Observability

VS-020 does not add new protocol messages or fields. It hardens the existing v1 flow around envelope size, malformed payloads, rate limits, controlled error responses and observability.

Gateway limits:

- anonymous handshake attempts are limited before WebSocket acceptance;
- authenticated `MoveIntent`, combat, inventory, heartbeat, join and reconnect messages are rate limited by category;
- payloads larger than 64 KiB are rejected before full Protobuf parsing;
- truncated or malformed Protobuf bytes return controlled `ServerError` payloads.

Observability:

- structured logs include timestamp, service, environment, trace id, connection id, account pseudonym, character id, map id, event type, result, error code and latency fields;
- logs and traces must not contain passwords, access tokens, game tickets, reconnect tokens or full sensitive payloads;
- OpenTelemetry activity names cover authentication-ticket-join, move intent, kill-reward-inventory-delta, equip-validation-persistence and disconnect-checkpoint-reconnect.

The load bot contains the automated VS-020 offensive/defensive gate for rate limits, large payload, truncated Protobuf, handshake spam, reconnect during reward, duplicate reward blocking and short soak smoke. The full 2 hour soak remains a release gate profile.

## Compatibility

Future compatible changes may add new field numbers without reusing or changing existing field meaning. Incompatible changes require a new package version such as `divinity.protocol.v2`.

Fields already assigned in v1 must not be renumbered. Client-authored payloads must remain intent-only.
